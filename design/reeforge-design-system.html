Reeforge design system

Shared visual base for every app in the Reeforge hub, starting with Reeforge Finance. Reef is the ocean: deep blue, calm, trustworthy, with light coming from above. Forge is the ember: the mark of something being made. Cool basalt is the ground they share. Reforge lives in motion: things visibly get better. Source of truth: DESIGN.md and design/tokens.css.

À valider

Cette page présente l'identité visuelle commune à toutes les applications Reeforge, en commençant par Reeforge Finance. Les écrans sont des exemples avec des données fictives. Voici les six décisions sur lesquelles on attend votre accord.

1

Couleurs

Bleu océan pour tout ce qui est cliquable, braise (orange forge) réservée à un seul chiffre clé par écran, neutres « basalte » légèrement bleutés. Le nom Reeforge s'y lit : reef (l'océan), forge (la braise), reforge (l'amélioration, dans les animations).

2

Typographie

General Sans pour les titres et les chiffres clés, IBM Plex Sans pour l'interface et les tableaux, IBM Plex Mono pour les identifiants (numéros TaxCore, certificats).

3

Interface vivante

Un fond océan qui bouge lentement, vu à travers du verre dépoli (barre du haut, menu, chiffres clés, fenêtres). Les tableaux et formulaires restent opaques pour que les montants soient parfaitement lisibles.

4

Clair et sombre

Les deux thèmes dès la première version. Essayez le sélecteur Light / Dark en haut de la page.

5

Anglais et bislama

Un sélecteur de langue sur la connexion et dans l'application. Le bouton « Long strings test » allonge tous les textes pour vérifier que le bislama tiendra.

6

Règles produit

Le mode Sandbox est toujours visible ; le bouton principal suit la situation (« Retry failed » quand des factures ont échoué) ; un seul chiffre en couleur par bandeau, celui qui demande une action.

Comment répondre. Laissez vos remarques en commentaire sur cette page, en citant le numéro de la décision (par exemple « 3 : moins d'animation »). Sans remarque, on considère l'ensemble validé.

Colors

Basalt neutrals carry the page, ocean blue marks what you can act on, lagoon supports it, ember is rare and marks what matters most. The interface is alive: a slow fluid ocean drifts behind frosted-glass chrome (top bar, sidebar, stats, modals), while tables and forms stay near-opaque so figures read perfectly.

  • Ocean blue = interactive: primary buttons, links, focus ring, selected nav and rows. Lagoon = info messages and chart series 3.
  • Glass (.rf-glass) only on chrome: top bar, sidebar, stats strip, modals, toasts, login. Never behind tables, forms or long text: those use --rf-surface-data (94% opaque).
  • Fluid background (.rf-fluid): one per page, three ocean blobs (ocean, lagoon, deep), slow (38s), stops with reduced motion. No ember in the background: diluted, it turns pink and reads as an error.
  • Gradients only through tokens: --rf-gradient-primary (buttons, avatar, checked controls), --rf-gradient-ocean (login and onboarding panels), --rf-gradient-page (page top). Never blue-to-purple, never on text.
  • Ember = the hero figure when nothing needs action, one highlight per chart (never a whole series), brand moments. Never for status, errors or buttons.
  • Ember as text only at 20px or larger, or use --rf-accent-strong (5:1 on white).
  • Status colors always come with a word ("Fiscalized", "Failed"), never color alone.

Buttons

One primary button per view: the main thing this screen is for. Labels start with a verb and name the outcome.

Variants
Sizes · sm 32 · md 36 (default) · lg 44 (login, empty states)
States
  • Good labels: "Fiscalize invoice", "Connect Xero", "Upload certificate", "Retry failed (3)". Avoid: "Submit", "OK", "Click here".
  • Destructive actions use danger and always confirm in a modal that names what is lost.
  • Loading: keep the button width, show the spinner, and say what is happening ("Sending to TaxCore…").
  • Disabled buttons say why in their label or a tooltip. Prefer enabled + inline error when possible.

  • Every table has four states designed: loading (skeleton rows), empty (an invitation with one action), error (danger alert above the table with a retry), and long content (truncate with a tooltip, never wrap identifiers).
  • Row height 44px, compact 36px for dense admin lists. Header 36px, 12px semibold, muted.
  • Filters vs tabs: tabs (rf-tabs) switch between sections of a page; status filters inside a section use the segmented control (rf-segmented) with counts. Never two rows of identical tabs. The default filter is always "All".
  • Row actions live in a "…" menu (rf-menu). Destructive actions go last, after a separator, in red, and still confirm in a modal. Never a red "Delete" link on every row.
  • Pagination only when there is more than one page. With a single page, no footer buttons.
  • Filtered empty state: name what is empty ("No fiscalized invoices yet") and offer the way back ("Show all invoices"). Never "No invoice has this status".

Do and don't

Do

  • Use only --rf-* tokens; never a raw hex in a page.
  • Show the TaxCore environment on every screen.
  • Right-align amounts with tabular figures; identifiers in mono.
  • Design loading, empty, error and long-content states with the happy path.
  • Write labels as verb + object, in sentence case.

Don't

  • Use ember for a button, a status or an error.
  • Put a panel inside a panel.
  • Use colored left borders on cards or alerts.
  • Invent gradients outside the tokens, add glows, or put tables and forms on see-through glass.
  • Rely on color alone to convey a status.
